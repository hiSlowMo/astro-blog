博客搭好以后，我一直想解决一个很实际的问题：离开电脑，还能不能方便地写点东西？

我的文章和说说本来就是 Markdown 文件，Astro 在构建时读取它们，Vercel 负责部署。技术上当然可以在手机上编辑 GitHub 文件，但那不是一个适合随手记录的界面。于是我接入了 Pages CMS，让它直接编辑仓库里的内容，而不另外引入数据库和独立后端。

这次做完之后，手机上的流程变成了：打开 Pages CMS，写正文，保存，等 Vercel 部署完成。

不过，真正让我多花了一点时间的不是配置字段，而是测试草稿时发现的时间偏差。

## 为什么没有引入一套新的内容系统

我希望 Pages CMS 只是一个编辑器，博客的内容仍然属于这个仓库。

文章继续放在 `src/content/posts`，说说继续放在 `src/content/moments`，图片放到 `public/uploads`。保存操作生成普通的 Git 提交，Vercel 仍然根据 `master` 分支自动部署。

这样做的好处是，离开 Pages CMS 以后，我依然可以在电脑上用熟悉的编辑器写作。即使以后不再使用它，文章、图片和 Git 历史也不会被某个服务绑住。

登录 Pages CMS 后，选择 `hiSlowMo/astro-blog` 的 `master` 分支，再授权 GitHub App 访问这个仓库即可。后台读取的配置就是根目录的 `.pages.yml`。

## 把现有内容结构映射到后台

配置的核心是两个 collection：文章和说说。

```yaml
content:
  - name: moments
    label: 说说
    type: collection
    path: src/content/moments
    format: yaml-frontmatter

  - name: posts
    label: 文章
    type: collection
    path: src/content/posts
    format: yaml-frontmatter
```

文章除了标题和正文，还有摘要、标签、分类、封面、系列、置顶和可见性等字段。这些字段与 `src/content.config.ts` 中的 Astro schema 对应，后台保存的是 YAML frontmatter，并不是另一套数据格式。

几个细节是专门为现有博客保留的：

- 正文使用 Markdown 文本框，避免富文本转换改写 Ruby 注释、公式、提示块和图片宽度。
- 新文章默认开启草稿，保存到仓库不代表立即公开。
- 新文件使用日期和时间命名，避免中文标题被转换成空的 slug。
- 已有文章禁止在后台重命名，避免修改标题时顺带改变 URL 和评论对应关系。
- 开启 `content.merge`，编辑时合并原有 frontmatter，减少遗漏字段的风险。

说说则简单得多：正文、发布时间和草稿开关。新建时会自动生成文件名和时间，适合临时记一段话。

## 不能只确认配置文件存在

`.pages.yml` 提交到 GitHub，只能说明配置已经就位，不能说明后台真的可用。

所以我在浏览器里完整走了一遍：登录账号，打开仓库，读取说说和文章，新建一条测试草稿，然后保存。

测试文件确实提交到了 GitHub，提交信息也是配置里的“发布说说：文件名”。Vercel 随即开始构建，最后状态变成 Ready。网站没有显示测试草稿，已有说说正常保留。确认之后，我通过 Pages CMS 删除了测试文件，本地再执行 `git pull --ff-only` 同步删除提交。

图片库也确认能够正常打开，不过那次没有实际上传图片，因此它不属于这次已经完成的实测范围。

到这里，保存和自动部署链路已经通了，但还不能说配置完全正确。

## 草稿暴露了八小时的时间偏差

第一次测试时，我在北京时间 09:51 新建草稿，保存到 GitHub 的时间却是：

```yaml
published: 2026-11-03T09:51:00Z
```

末尾的 `Z` 表示 UTC。`09:51Z` 换算成北京时间其实是 17:51，正好晚了八小时。

问题不在 Astro 的渲染，而在 Pages CMS 的日期字段。浏览器提交的是不带时区的本地时间，例如 `2026-11-03T09:51`；保存时，服务端按 UTC 解释并格式化。配置中的 `XXX` 又让服务器输出自己的 UTC 时区，于是本地钟点被错误地当成了 UTC 钟点。

修复方式是把北京时间偏移写成格式中的字面量：

```yaml
options:
  time: true
  format: "yyyy-MM-dd'T'HH:mm:ss'+08:00'"
```

关键是最外面的双引号，以及 `+08:00` 外面的单引号。单引号让 date-fns 把它作为固定文本输出，不再替换成服务器的时区。

文章的发布时间和更新时间也采用同样方式，只是保留毫秒：

```yaml
format: "yyyy-MM-dd'T'HH:mm:ss.SSS'+08:00'"
```

这依赖博客内容统一使用北京时间。对当前固定使用 `Asia/Shanghai` 的博客来说，它比依赖服务器所在时区更明确。

## 历史时间只换写法，不换时刻

已有文章有些保存成 `Z`，有些保存成 `+08:00`。如果直接给旧时间补一个后缀，就会改变它们的真实发布时间。

所以历史文章先把 UTC 时间转换为北京时间，再替换后缀。例如：

```yaml
# 修改前
published: 2026-02-15T17:01:23.526Z

# 修改后
published: 2026-02-16T01:01:23.526+08:00
```

这两行看起来差了八小时，实际指向同一个时刻。转换时逐个比较了解析后的时间戳，12 个历史发布时间和更新时间全部保持一致。

电脑端的 `new-post` 脚本也统一输出 `+08:00`，这样无论从 Pages CMS 还是本地脚本创建内容，时间格式都一致。

## 最后再走一次真实保存

修复推送到 `master` 后，我重新加载后台。历史说说的 21:00 不再显示成 13:00，文章的发布时间和更新时间也能正确回填。

第二次测试草稿中，表单填写北京时间 10:01，GitHub 中得到：

```yaml
published: 2026-11-03T10:01:00+08:00
draft: true
```

重新打开这条草稿，表单仍然显示 10:01。这说明不只是保存格式对了，读取已有时间时也没有再次发生偏移。

本地完整构建、内容回归检查以及针对 UTC、上海、洛杉矶三个运行环境的日期读写测试均通过。测试草稿随后删除，工作区也同步到了最新提交。

现在，Pages CMS 在这个博客里承担的只是一个足够轻的写作入口：内容仍是 Markdown，发布仍由 Git 和 Vercel 完成，而真正需要小心处理的，是这些看起来不起眼的字段细节。
