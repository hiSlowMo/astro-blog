今天无意中点开 <ruby>五月七日千緒<rt>Tuyuri Tio</rt></ruby> 的博客，也就是“記緒漂流”，他的网站设计我第一次见到就喜欢上了——克制，情绪，简约，设计。点进links页，报刊的视觉设计，每个友链都被刊载在报纸的版面上，我决定“申请刊载”，也决定受此感发重构我的links页-THE SLOWMO RECORDS 。

THE SLOWMO RECORDS 是一个唱片专辑收录页。

每个友链是一张专辑，封面、作者、类型和代表文章都摆在应该在的位置。接下来问题来了，我如何实现的展示<ruby>最新曲目<rt>最新文章</rt></ruby>以及<ruby>推荐专辑<rt>申请友链</rt></ruby>呢？

样子已经有了，柜台后面却还没有人。

哎呀，当然是去问ChatGPT啦。

不过，这次我不想要一张只有效果的截图，也不想要一个点下去只会告诉我“提交成功”的表单。

我想要的是，它真的能接收一张新的专辑，真的能在我不知道的时候更新曲目，也真的能在有人敲门的时候通知我。

于是我把这个念头交给了 Codex。

## 先把唱片店的样子想清楚

我并不想把友链页做成一排密密麻麻的卡片，也不想为了显示更多内容，把每个博客压缩成一个小小的头像。

一个博客最值得被看见的，从来不只是名字和链接。它还有作者正在写什么，最近关心什么，以及那些只有点进去才能感受到的气质。

所以，THE SLOWMO RECORDS 借用了一张专辑的结构：网站是专辑，博主是音乐人，文章是曲目。封面、编号、类型标签和简介构成它的档案，代表文章则像主打歌，决定你要不要把这张唱片拿下来听一听。

页面上保留了三个部分。NOW SPINNING 是随机选曲，NEW ARRIVALS 是新近上架，THE COLLECTION 则是完整的唱片目录。常用网站被放进 FROM THE CRATE，不必硬装作博客，也不必占用专辑的位置。

桌面端是双列陈列，手机上自然收成单列。但移动端并不是简单地把所有东西从上往下堆起来：专辑封面和站点信息仍然并排，标题、日期与文章链接有各自的层次。毕竟在手机那么窄的屏幕上，封面和信息各独占一行，一张专辑就只剩下一次漫长的滚动。

随机推荐加上了 `SHUFFLE ON`，阅读入口是 `READ TRACK`。这些英文不是为了让页面显得“国际化”，更像是唱片机上真正会亮起来的小指示灯。

深色和浅色主题也都保留下来。它们是同一家唱片店在白天和晚上的两种光线，而不是两套互不相干的页面。

## 我不想为了三篇文章重新部署一次

页面做好之后，最显眼的问题也随之出现了。

友链数据原本就在博客仓库里。想修改一张专辑的曲目，就要编辑 TypeScript 文件，提交，再等一次构建。对于交换友链这件事，这样做并没有问题；但如果“最新文章”永远只能停留在上一次部署的时候，那它就不能叫最新。

最直观的办法是打开页面时，由浏览器逐个抓取所有博客的 RSS。这样看似不需要后端，实际上却把等待、跨域、失败和各不相同的 Feed 格式全都推给了访客。

我不喜欢这个方案。

最后采用的是很普通的一层后端：服务器负责定时抓 Feed，数据库保存最近一次成功的结果，页面只向一个统一接口要数据。

```text
GET https://api.theslowmo.com/records/v1/tracks
```

返回的每张专辑最多保留三首曲目，包括标题、链接、发布时间和摘要。浏览器拿到结果后，再替换页面里的曲目与随机选曲。

这里有一个很重要的顺序：**先展示已有内容，再异步更新。**

Astro 仍然把仓库里的友链和文章渲染进 HTML。即使 API 暂时不可用，页面也不是一片空白；请求超时、返回异常或者某篇文章的链接无效，就安静地保留原来的内容。RSS 的更新不应该成为打开友链页的前置条件。

## 每半小时，替我去看看大家在写什么

真正的抓取发生在服务器上，而不是访客的浏览器里。

已收录的站点可以继续显式配置 RSS 或 Atom 地址；没有配置时，后端会尝试从首页的 `alternate` 链接发现 Feed。解析后按发布时间排序，清理摘要里的 HTML，按文章链接去重，只留下最新三篇。

同步交给 systemd timer，每三十分钟执行一次：

```ini
[Timer]
OnCalendar=*:0/30
Persistent=true
```

`Persistent` 很有必要。服务器如果恰好错过了某次任务，恢复运行后还可以补上，而不是假装什么都没有发生。

抓取也没有被写成“失败就清空重来”。某个 Feed 超时、格式损坏，或者一篇文章没有有效链接，都不应该抹掉这个博客以前的记录。只有完整拿到并解析出有效文章后，才替换该站点上一次成功的快照。

没有 RSS 的博客仍然可以继续手工维护曲目。这不是一套只允许标准博客加入的系统，也不是为了自动化，反过来要求每个人都必须先提供某种格式的文件。

自动化应该减少维护，不应该增加门槛。

## 柜台后面，终于有人收件了

“推荐一张专辑”的表单也接上了真实接口：

```text
POST https://api.theslowmo.com/records/v1/applications
```

网站名称、地址、博主昵称、邮箱、简介、图标和 RSS 等信息，会先经过服务端校验，再完整保存到 SQLite。每份申请得到一个 `SR-` 开头的唯一编号，状态默认为 `pending`。
![邮件成功转发到我的Gmail邮箱](https://img.theslowmo.com/2026/11/d9182f07ecb26b45ab17c66898e86603.webp "width=78%")
前端不再自己制造一个成功提示。只有服务器真正保存成功，并返回 `201` 和申请编号后，页面才会告诉访客“申请已收到”。字段有误、站点已经存在、已有相同申请或提交过于频繁，都会得到对应的失败结果。

垃圾提交则通过隐藏字段、来源限制和频率控制处理。它们不一定能挡住所有自动化请求，但对于这样一个不需要登录的小表单，已经足够作为第一层门槛。申请仍然需要人工审核，提交成功不等于自动收录。

我没有为它再做一套复杂的管理后台。现在更重要的是把保存、查看和审核之间的边界做好，而不是先造出一个以后未必会使用的大系统。

## 收信和发信，原来是两件事

邮件通知是这次很容易想当然的一部分。

我已经使用 Cloudflare Email Routing，把 `me@theslowmo.com` 转发到自己的常用邮箱。所以一开始很容易误以为：既然域名邮箱能够收信，那服务器直接用它发一封通知就行了。

但 Email Routing 解决的是收件和转发，并不会因此让华为云获得主动发信能力。单独搭建邮件服务器更不在我的计划里。为了偶尔收到一份友链申请，去维护 IP 信誉、反向解析和投递策略，显然有些得不偿失。

最后使用的是 Cloudflare Email Sending。华为云只调用一个带独立密钥的通知 Worker，由受限的邮件绑定发送到现有域名邮箱，再沿用原来的 Email Routing 到达我的收件箱。

我在手机上打开通知邮件，就能看见站点简介、博主的联系方式和代表文章，顺手点进对方的博客逛一圈。决定收录的话，把邮件里的申请编号交给 Codex 就行。华为云也留着完整记录，之后还查得到。

而且**保存申请在前，发送通知在后**。如果邮件服务暂时失败，申请不会跟着消失，后端会保留待通知状态并稍后重试。邮件没有送达和申请没有收到，必须是两件可以被区分的事。

第一阶段只通知我，不给申请人自动回信。少一步自动化，也少了很多不必要的复杂度。

## 华为云，终于不再只是一台开着的机器

这套后端没有引入大型框架。Flask、Gunicorn 和 SQLite 已经足够，服务只监听本机地址，由 systemd 负责开机自启和异常重启。Feed 同步、邮件重试和每日备份各自使用独立定时任务，SQLite 每天生成经过完整性检查的快照，保留最近十四份。

`api.theslowmo.com` 上原本还有 Magpie，不能为了一个新接口把原有服务覆盖掉。所以最终只把 `/records/v1/*` 交给 Records，通过专用 SSH 隧道转发到华为云，域名上的其他请求仍走原来的路径。Cloudflare 已有的 DNS 和邮件转发配置也不需要推翻重来。

这部分是我觉得 Codex 的 SSH 和 cf CLI 技能真正好用的地方。

它并不只是给我一份“请在服务器执行以下命令”的教程，而是能够先检查现有系统、端口、服务和 DNS，再决定新服务应该放在哪里。Systemd 单元、定时器、文件权限和备份策略可以直接落到服务器上，执行后再读取真实状态。哪里没有跑起来，也能继续查日志，而不是停在一个看似完整的配置文件上。

cf CLI 也同理。Cloudflare 配置不再需要在一层层后台页面里反复寻找，Worker 的发布可以先做 dry-run，再部署，再请求真实地址确认结果。查看和修改之间也有比较清楚的界限，这让我敢把它用在已有服务旁边，而不只是在一个随便折腾的空项目里。

对我来说，这两个技能最有价值的地方不是省下了几条命令，而是把“本地写好的代码”和“远处正在运行的服务”接了起来。终端不再只是生成文件的地方，它可以真正抵达部署现场。

## 一家需要慢慢营业的唱片店

这次做完以后，THE SLOWMO RECORDS 不再只是一个换了皮肤的links页。

它会把友链作者的新文章慢慢收进来，会在访客不知道点什么的时候随机递出一首曲子，也会把一份申请真正保存下来，再等我有空时处理。

当然，它现在依然很简单。审核还是人工的，备份也还应该继续增加异机副本，邮件通知能告诉我“有新申请”，却不能替我判断一个网站是否值得收录。

但这些留白并不是坏事。

我原本想要的就不是一套功能齐全的友链管理系统，只是一家属于自己的小唱片店。有人路过，翻翻封面；有人留下一张专辑；而在没有更新页面的那些日子里，唱片架上的曲目仍然在悄悄变化。

现在，柜台后面终于有人了。
